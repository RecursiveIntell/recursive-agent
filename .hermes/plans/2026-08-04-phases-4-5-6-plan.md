## Current Architecture Summary

```
ra (CLI)
├── runner (sequential single-threaded RunSpecV1 walk)
│   ├── policy (Allowlist: echo, time_now, llm, shell)
│   ├── tools (dispatch: match tool name → typed execute)
│   │   ├── provider (ollama | openai_compatible)
│   │   └── sandbox (user-ns + Landlock fork/exec)
│   ├── contracts (RunSpecV1, StepSpecV1, ReceiptV1, lineage)
│   └── ledger (receipts.ndjson, artifact store, verify, replay)
```

Tool dispatch is a flat match statement in `tools/src/lib.rs:74-117`. Every tool call flows through: policy authorize → tool execute → ledger append. All receipts are JCS-canonicalized, BLAKE3-chained.

**Risks / open decisions:**
- **MCP transport choice**: stdio only first (simplest, Hermes-compatible). TCP is a follow-up behind an auth gate.
- **Daemon auth model**: Phase 4 daemon has no authentication — it runs on a Unix socket with filesystem permissions (`0600`). Phase 6 adds operator auth.
- **Concurrent runs**: single-threaded runner today. Daemon needs a run queue (tokio::spawn per run, bounded semaphore). First pass: serialize runs (accept→execute→respond), then add concurrency.

### Agent Delegation (extends runner)

Add a `delegate` tool to the existing tool dispatch:

```rust
// tools/src/lib.rs addition:
"delegate" => {
    let parsed: DelegateArgs = serde_json::from_value(call.args.clone())
        .map_err(|e| ToolError::Args(format!("delegate: {e}")))?;
    // The delegate tool spawns a child ra process with the sub-spec.
    // Output flows through the same receipt chain.
    let result = spawn_child_run(&parsed.spec_path, &parsed.timeout)?;
    Ok(serde_json::to_value(result)?)
}
```

Delegation creates a sub-run directory under `<parent-run>/delegates/<run-id>/`. Parent receipt references the child run-id. Child receipt chain is independently verifiable. This preserves the receipt-chain contract while adding hierarchy.

### Monte Carlo Tree Search (new crate: `recursive-agent-mcts`)

```
crates/recursive-agent-mcts/
├── Cargo.toml
├── src/
│   ├── lib.rs
│   ├── tree.rs       — MCTS node, selection (UCT), expansion, backprop
│   ├── rollout.rs    — execute a random/completion-guided path, score result
│   └── policy.rs     — tool-specific heuristics (prefer read over write, etc.)
└── tests/
    └── mcts_tests.rs
```

**Approach**: MCTS searches over *tool sequences* (which tool to call next, with what args skeleton). Each rollout executes a complete run spec through the deterministic runner (provider calls become recorded artifacts after first real call). Scoring: task-completion signal + receipt-chain length + artifact relevance.

This is the most experimental phase. Start with a bounded search (100 rollouts, 10-step max depth) on a fixed task family (e.g., "find and summarize files matching pattern X").

**Phase 5 verification gates:**

```bash
cargo test -p recursive-agent-memory --all-targets
cargo test -p recursive-agent-skills --all-targets
cargo test -p recursive-agent-mcts --all-targets
cargo test --workspace  # ensure delegation doesn't break existing suites
cargo clippy --workspace --all-targets -- -D warnings
# Smoke: run a spec that uses memory_put → memory_search → echo cycle
```

**Risks / open decisions:**
- **Vector search dependency**: `candle` or `ort` for embeddings is heavy. Feature-gate it; BM25 is sufficient for Phase 5 MVP.
- **Skill registry storage**: File-system first (`~/.local/share/recursive-agent/skills/`), SQLite later. Keep it simple.
- **MCTS rollout cost**: Each rollout calls providers (expensive). First pass: use deterministic mock provider for rollouts, then re-rank top-K with real provider.
- **Python sidecar**: Deferred. The M0 report mentions it for Monte Carlo benchmarking. If needed, add a `python-bridge` feature that shells out to a venv-managed script. Not required for Phase 5 core.
